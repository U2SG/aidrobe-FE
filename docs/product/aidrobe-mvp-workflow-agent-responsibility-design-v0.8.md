## 0. 设计理念：悦己，而不是管理

Aidrobe 的产品原点不是"衣橱管理"，也不只是"穿搭效率"。

它的情感原点是：

```text
悦己
```

用户不是为了维护一套衣物数据库而打开 Aidrobe。  
用户真正想要的是：

```text
每天少一点纠结，
多一点确定，
穿成自己喜欢的样子。
```

早期 slogan 讨论里有几个方向应该成为 Aidrobe 的长期产品气质：

```text
今天，穿成喜欢的自己。
穿给自己看，取悦每一天。
打开衣柜，也打开今天的自己。
衣橱不只是收纳，是我爱自己的方式。
衣以载心，容以悦己。
```

这些不是简单的 landing page 文案，而是产品方向约束。

它们意味着 Aidrobe 不应该被设计成：

```text
一个管理衣服的工具
一个展示穿搭的社交产品
一个刺激购物的消费产品
一个审判用户衣橱的健康分系统
```

Aidrobe 应该更像：

```text
一个每天安静工作的私人穿搭 agent。
```

它帮助用户把衣服、天气、时间、心情、场景和审美重新连接起来。

## 0.1 情感北极星与功能北极星

Aidrobe 有两个北极星。

### 情感北极星

```text
今天，穿成喜欢的自己。
```

这是用户最终感受到的价值。

不是"今天穿得最优"，也不是"今天穿得最时尚"，而是：

```text
这套是我愿意穿出去的。
这套像我。
这套让我轻松一点。
```

### 功能北极星

```text
不用想，今天穿什么已经准备好了。
```

这是产品要交付的能力。

情感北极星决定产品气质。  
功能北极星决定 workflow。

二者合在一起，就是 Aidrobe MVP 的方向：

```text
用 agent 的复杂能力，服务用户的简单悦己。
```

---

## 0.2 "做自己的芭比娃娃"的产品解释

"做自己的芭比娃娃"这个方向有价值，但要把它翻译成更成熟的产品语言。

它真正表达的不是幼态化，也不是把用户物化成娃娃，而是：

```text
把自己当成最喜欢的角色来照顾和装扮。
```

这里面有三层含义：

```text
1. 主权在用户：用户决定自己想成为什么样子
2. 乐趣在搭配：穿衣不是任务，也可以是轻仪式感
3. 执行交给 agent：系统帮用户降低整理、选择、判断成本
```

所以 Aidrobe 不应该说：

```text
AI 告诉你怎么穿。
```

而应该是：

```text
AI 帮你更容易穿成喜欢的自己。
```

Agent 不是审美权威。  
Agent 是用户自我表达的助手。

## 0.3 产品气质：温柔、具体、克制、可信

Aidrobe 的语气不应该像营销号，也不应该像教练训话。

应该避免：

```text
你应该这样穿
你这样更高级
你的衣橱不健康
你浪费了很多衣服
这件必须买
这样才显瘦
```

应该使用：

```text
这套更接近你最近喜欢的冷调通勤感。
今天有雨，所以先避开浅色鞋。
这几件最近没怎么出现，可以重新利用。
如果想少带行李，这件外套可以覆盖两天场景。
```

产品语气应遵循：

```text
温柔，但不空泛
具体，但不啰嗦
克制，但不冷淡
可信，但不装懂
```

（推荐 / 空状态 / 反馈 / insight 的具体文案规范，统一收在 §6.5 Tone of Voice，避免散落重复。）

## 0.4 设计原则总纲

后续所有 workflow 都应服从这四个总纲。

### 1. 悦己优先，不制造焦虑

Aidrobe 不应该用焦虑驱动使用。

避免：

```text
你穿得不够好
你的衣橱有问题
你需要买更多
你需要更时尚
```

追求：

```text
你已经拥有的衣服，可以被更好地使用。
```

### 2. 用户主权，Agent 辅助

用户拥有审美主权。  
Agent 只做理解、整理、规划、推荐和学习。

产品不应该让用户感觉：

```text
我被 AI 指挥。
```

而应该让用户感觉：

```text
它在帮我把想法变简单。
```

### 3. 少操作，多理解

用户越少操作，agent 越要承担更多理解工作。

用户只需要自然表达：

```text
我喜欢这种感觉
今天不想太正式
这套不像我
下周去东京帮我打包
```

系统负责把自然语言 / 图片 / 行为转成结构化信号。

### 4. 真实可信，不装个性化

所有个性化都必须有依据：

```text
真实衣物
真实天气
真实历史
真实偏好
真实反馈
真实风格学习
```

没有依据时，宁可诚实说不足，也不要伪装成智能。

## 0.5 目标用户：为谁做

Aidrobe MVP 不为所有人做，但也不能把女性视角窄化成某一个年龄段。

目标用户应该覆盖：

```text
20–60 岁女性
```

但产品不是按年龄做，而是按 **衣橱行为 + 生活状态** 做。

Aidrobe 的核心用户不是两个极端：

```text
不是衣橱极简、只追求极致省事的人
不是热爱搭配、什么都想自己掌控的时尚玩家
```

而是夹在中间、人数更大、生活场景更多的那群：

```text
她有一定数量的衣服。
她在乎穿出来的状态。
她不想每天被搭配消耗。
她总是在少数几件衣服里反复循环。
她知道自己衣柜里还有很多"被忘了"的衣服。
她想穿得像自己，而不是被 App 教训或改造。
```

她可能是 20 岁，也可能是 60 岁。  
年龄不是边界，真实边界是：

```text
衣橱不小，但利用率低
在乎结果，但不想花太多心力
希望更轻松地穿成喜欢的自己
愿意被理解，不愿意被审判
```

所以更准确的目标用户画像是：

```text
20–60 岁女性；
衣柜里有一定存量；
反复穿的只有其中一小部分；
每天或重要场景前会产生穿搭决策压力；
希望 Aidrobe 帮她少纠结、少浪费、少买错，
并重新穿回那些被忘记但仍然适合自己的衣服。
```

她的共性不是年龄，而是这些生活感受：

```text
"一柜子衣服，却没衣服穿。"
"怎么又穿这几件？"
"这件买了很久还没穿过。"
"我想体面一点，但不想太用力。"
"我想舒服，但也想像自己。"
"我不想被评价身材，也不想被催着变时尚。"
```

这个用户决定了 MVP 的所有取舍：

```text
省事优先：她不想选，给一套能信的，不给一份菜单
默认全自动：平时什么都不碰，特殊场合说一句话就能调
重新使用：把她忘了的衣服重新穿起来，比劝她买新的更打动她
不押在打卡上：她不会天天记录，learning 不能悬在"穿了"按钮上
不审判身体：不默认使用显瘦、遮肉、修饰缺陷等规训型语言
跨阶段适配：不同年龄 / 生活阶段有不同约束，但都需要更轻松地穿对
```

后面每一个 workflow 的取舍，都应该回到这个人身上检验：

```text
这一步对她是省事，还是负担？
这句话让她被理解，还是被审判？
这套推荐是在帮她生活，还是让她继续选择？
```

## 0.5.1 Life-stage Segments：20–60 不是一个人，但可以共用一个 Agent

20–60 女性不能被压成一个单一 persona。  
更好的方式是：共用同一套产品原则，但让 agent 根据生活阶段、衣橱行为和反馈自动调节。

> **定位提醒（v0.8）：life-stage 推断是 north-star，不是 v1 capability。**
> 本文档自己定的原则是"从行为里学，不问问卷"。但冷启动时几乎没有行为——新用户刚导入，
> 系统手里没有足够信号去判断她更接近哪个阶段。所以现实里，early 阶段这套推断大概率不会稳定触发，
> 它更像一个**指导设计取舍的思考框架**，而不是能在 v1 交付、能写进验收的能力。
> 详见 §10 的发布顺序说明。下面的分段，请当作"产品取舍的约束清单"来读，而不是"v1 的功能模块"。

### 20–25：探索期 / 初入社会 / 风格未定型

她的典型状态：

```text
衣服数量可能不算最多，但风格变化快
容易被社交媒体 / 同龄人 / 新工作场景影响
想尝试，但不知道什么真的适合自己
购物冲动强，买回来的单品可能难搭
```

她需要 Aidrobe 做：

```text
帮她理解自己喜欢什么
帮她把灵感图落到真实衣橱
帮她少买难搭的单品
帮她在探索中保持可穿性
```

产品重点：

```text
Style Learning
Should-I-Buy 情境入口
Ask 一句话搭配
灵感图 → 真实衣橱转译
```

不应该做：

```text
强行给成熟职场模板
过早固定她的风格
用"高级感"压住探索欲
```

### 26–35：职场建立期 / 通勤高频 / 生活节奏快

她的典型状态：

```text
通勤、约会、聚会、旅行、工作混杂
衣柜逐渐变大，但每天仍然抓固定几件
想体面、有精神，但不想早上消耗
容易买"看起来能通勤"的重复款
```

她需要 Aidrobe 做：

```text
每天直接给一套
特殊场合一句话调整
帮她少买重复款
帮她把吃灰单品重新穿起来
```

产品重点：

```text
Today 单套推荐
Context Override
Resurface Insight
Should-I-Buy 防重复
```

### 36–45：多角色期 / 家庭与工作并行 / 时间稀缺

她的典型状态：

```text
时间被工作、家庭、孩子、社交切碎
想穿得得体，但不能太麻烦
更重视舒适、品质、好打理
可能拥有很多旧衣服，但不知道哪些还适合现在
```

她需要 Aidrobe 做：

```text
降低每天决策成本
避免难打理、难行动、易皱的推荐
帮她筛出仍适合当下生活的衣物
在不制造焦虑的前提下更新穿法
```

产品重点：

```text
Comfort / Mobility / Maintenance Cost
Wardrobe Resurface
低打扰反馈
轻量 Ask
```

不应该做：

```text
制造年龄焦虑
暗示她需要变年轻
过度推潮流
```

### 46–60：品质稳定期 / 舒适与自我表达并重

她的典型状态：

```text
更清楚自己喜欢什么
更重视面料、舒适、体面、场合合宜
不想被年轻化审美规训
可能有大量高质量旧衣，但缺少新的组合方式
```

她需要 Aidrobe 做：

```text
尊重已有审美
重新组合已有高质量衣物
根据天气、舒适度和场合做稳妥建议
在需要时提供轻微新鲜感，而不是强行改变
```

产品重点：

```text
Respectful Styling
Existing Wardrobe Recombination
Comfort-aware Recommendation
Occasion Fit
```

不应该做：

```text
默认追求显年轻
默认推荐流行趋势
默认用身材修饰话术
```

### 共用原则

虽然生活阶段不同，但 Aidrobe 对所有 20–60 女性都应保持一致：

```text
不审判
不催买
不强行定义美
不制造身材焦虑
不把复杂配置丢给用户
不把推荐做成选择题
```

Agent 应该根据用户行为逐渐判断她更接近哪种生活状态，而不是一开始问一份年龄/职业问卷。

默认方式：

```text
先给一套可信的
从反馈和行为里学习
必要时只问一句
```

## 0.6 女性生活约束：穿搭是一天的状态管理

对目标用户来说，穿搭不是一道单纯的审美题。  
她早上面对衣柜时，真正要处理的是一天的状态。

她不是只在问：

```text
这套好不好看？
```

她同时在问：

```text
今天冷不冷？
今天要不要见客户？
今天要不要走很多路？
这双鞋能不能撑一天？
办公室空调会不会冷？
这件会不会皱？
下雨会不会弄脏？
今天状态好不好？
今天想被看见，还是想低调一点？
```

所以 Aidrobe 不应该只做 style compatibility。  
它应该理解女性一天里的真实约束：

```text
comfort 舒适度
mobility 行走 / 通勤负担
weather tolerance 天气容错
social context 社交 / 职场场景
energy level 当天能量感
visibility level 今天想不想被注意
maintenance cost 是否易皱 / 难打理 / 容易弄脏
```

Aidrobe 推荐的不是"理论上最会穿"的一套，而是：

```text
今天能安心穿出去的一套。
```

这会影响推荐逻辑：

```text
通勤日：先保证可走、可坐、不过度用力
会议日：干净、得体、有精神，但不自动推到最正式
雨天：避开浅色鞋、拖地裤、难清洁材质
低能量日：优先舒适、有安全感、少配饰
想被看见：允许更有风格表达，但仍要真实可穿
```

这也会影响文案语气：

```text
今天要走路多，这双鞋比乐福鞋更稳。
今天有会，但不是正式汇报，不用上到西装外套。
今天偏冷，这件薄外套可能不够，先换成羊毛外套。
```

这个原则把 Aidrobe 从"穿搭建议 App"推进到：

```text
女性日常状态管理里的穿搭 agent。
```

## 1. 核心判断

Aidrobe 现在已经不再是"缺功能"的阶段。

过去一轮已经完成了大量底层能力：

```text
衣物导入
多件确认
Today recommendation
Ask Aidrobe
preference memory
multi-turn conversation
wardrobe graph
feedback signals
recommendation eval
wardrobe health
Should-I-Buy
style learning
visual style learning via Qwen-VL
```

这些能力说明工程基础已经具备。  
但 MVP 不能继续按"功能清单"推进。

现在必须切换到：

```text
Workflow first
User action minimization
Agent responsibility maximization
```

也就是：

```text
功能可以复杂，但用户必须简单。
复杂性应该被 agent 吞掉，而不是暴露给用户。
```

Aidrobe 的 MVP 目标不是让用户管理一个衣橱数据库，而是让用户感受到：

```text
每天打开，Aidrobe 已经知道我今天该怎么穿。
```

---

## 2. MVP 北极星体验

Aidrobe MVP 的体验表达可以分成两句。

面向用户的情感表达：

```text
今天，穿成喜欢的自己。
```

面向产品能力的功能表达：

```text
不用想，今天穿什么已经准备好了。
```

更完整一点：

```text
Aidrobe 自动理解我的衣橱、天气、偏好、风格和最近穿着，
在我每天打开 App 时给出一套可信、可解释、可反馈的穿搭建议。
```

这意味着 MVP 的核心不是：

```text
上传衣橱
管理衣橱
和 AI 聊天
看数据分析
购物建议
旅行打包
```

这些都是能力或场景。

MVP 的核心是：

```text
Daily outfit decision automation
```

也就是自动帮用户完成每天最常见、最高频、最烦的决策：

```text
今天穿什么？
```

---

## 3. MVP 主路径

MVP 只保留一条主路径：

```text
导入衣物
→ Agent 自动整理
→ 导入完成即出首套（激活时刻）
→ Today 自动推荐
→ 用户轻量反馈
→ 系统下次更懂
```

### Golden Path

```text
1. 用户导入第一批衣物
2. Agent 自动识别衣物、补全 metadata、理解风格
3. 用户只做必要确认
4. 导入完成即出首套（激活时刻，同 session，safe over clever）
5. 第二天打开 App
6. Today 给出一套推荐
7. 用户点击：穿了 / 换一套 / 不喜欢
8. Agent 自动学习并优化下一次推荐
```

这个闭环成立，Aidrobe MVP 就成立。

其他功能全部围绕这条主路径服务，而不是和它抢主入口。

---

## 4. MVP 不是什么

Aidrobe MVP 不应该是一个功能大全。

暂时不应该把这些能力放到主路径：

```text
复杂风格问卷
复杂衣橱健康 dashboard
复杂 packing planner
复杂购物决策页面
复杂 prompt 配置
复杂推荐偏好设置
复杂标签维护
```

这些功能可以存在，但不应该让用户觉得自己需要学习和管理。

MVP 阶段最危险的产品形态是：

```text
很多入口
很多按钮
很多设置
很多分析
很多 AI 解释
但用户不知道每天为什么打开
```

Aidrobe 必须避免成为"衣橱工具箱"。

## 4.5 不可再缩减的 MVP 核心

这份文档越写越长，覆盖了用户模型、情感北极星、八条 workflow、文案治理、前端重构。  
但越长越容易让人忘记一件事：**MVP 不是这些东西的总和。**

如果只能保留一句话，MVP 的核心是：

```text
新用户导入完一批衣服，当场就能看到一套
真实、可信、基于自己衣橱的搭配。
```

也就是 Workflow 0 的那条最短漏斗。它由三件**不可拆分**的事组成：

```text
导入完成即出首套（同 session）
safe over clever（首套挑最不会错的）
可行性 Gate（含渲染可行性）
```

这三件是一个包。只上"当场出首套"而不配 safe 策略和 Gate，  
等于把唯一的 aha 机会押在一套可能翻车的推荐上。

其余所有 workflow、原则、前端方案，都是这条核心的**排序问题**，不是**并列功能**。  
当不确定某个东西该不该进 MVP 时，回到一个判断：

```text
它是让"导入 → 看到可信首套 → 次日还想打开"这条线更稳，
还是只是又一个独立能力？
```

让线更稳的，靠前（P0 / P1）。  
只是又一个独立能力的，后置（P2 / later）。  
具体发布顺序见 §10。

## 5. 产品原则

### Principle 0: 悦己是方向，不是装饰

"悦己"不是一句品牌口号，而是 Aidrobe 的产品约束。

它要求所有推荐、文案、反馈、insight 都避免羞辱、焦虑和强消费导向。  
Aidrobe 的目标不是让用户买更多衣服，也不是让用户变成某种标准审美，而是帮助用户：

```text
更好地使用已有衣物
更少纠结每天选择
更稳定地穿成自己喜欢的样子
```

所以产品应该少说：

```text
你需要变得更时尚。
```

多做：

```text
帮用户在真实衣橱里找到今天能穿、愿意穿、像自己的那一套。
```

### Principle 1: 用户只做判断，不做配置

用户不应该被要求维护复杂数据。

错误方向：

```text
请选择你的风格偏好
请选择你的颜色权重
请选择你的场合偏好
请选择你的推荐策略
请选择今天推荐算法
```

正确方向：

```text
用户上传、穿、跳过、不喜欢。
Agent 自动学习。
```

用户的主要动作应该是：

```text
确认
穿了
换一套
不喜欢
```

而不是：

```text
填写
配置
管理
调参
```

---

### Principle 2: Agent 负责理解，用户负责生活

用户不应该为了让 Aidrobe 变聪明而额外劳动。

Agent 应该自动完成：

```text
识别衣物
补全标签
理解风格
推断场景
记住偏好
避免重复
解释推荐
吸收反馈
规划搭配
```

用户只需要自然地使用产品。

---

### Principle 3: 默认无感，必要时可干预

默认情况下，Aidrobe 不应该每天问用户很多问题。

Today 推荐默认使用：

```text
天气
位置
时间
最近穿着
衣橱状态
风格学习
偏好记忆
反馈历史
衣橱关系图
```

只有在用户主动表达特殊需求时才介入：

```text
今天有会议
今天想休闲一点
今天不想穿裙子
今天要走很多路
```

这类信息可以通过一句话输入，而不是表单。

对目标用户来说，这个一句话 override 是必需品，不是可选项：  
她平时什么都不碰，但遇到特殊场合，需要说一句就能调整，而不是被迫去翻设置页。

---

### Principle 4: 可信比炫酷重要

AI 产品最怕用户觉得它在"装懂"。

因此 MVP 必须避免：

```text
假 outfit
假图片
假 prompt
假理由
假个性化
```

所有推荐必须满足：

```text
引用真实衣物
理由来自真实上下文
图片正常显示
空状态诚实
不足数据时不要伪装成推荐
```

---

### Principle 5: 复杂能力隐藏在后台

这些能力应该存在，但不应显性打扰用户：

```text
preference memory
wardrobe graph
visual style learning
recommendation eval
feedback learning
packing constraints
wardrobe health scoring
```

用户看到的只是：

```text
它越来越懂我。
```

---

### Principle 6: 用户可见文案不硬编码，必须可治理

MVP 阶段尤其要避免硬编码用户可见文案。

硬编码文案的问题不是"代码不优雅"，而是会直接破坏产品可信度。  
对 AI 产品来说，用户一旦看到 demo prompt、固定推荐语、混合语言、无上下文文案，就会怀疑：

```text
这到底是不是根据我生成的？
还是只是 App 里写死的样例？
```

因此 Aidrobe 需要把 copy 当成产品系统的一部分，而不是散落在组件里的字符串。

#### 必须避免

```text
组件内写死用户可见文案
mock/demo prompt 泄漏到生产 UI
固定推荐理由
固定风格标签文案
中文/英文混杂
同一概念在不同页面叫法不一致
LLM 输出和产品 copy 互相冲突
```

典型风险词包括：

```text
雨天通勤
银蓝冷调
适合今天
很百搭
看看这套
示例搭配
local showcase
sample outfit
```

这些如果不是来自真实上下文、i18n 资源或 API 结果，就不应该出现在生产 UI。

#### 正确方向

所有用户可见文案都应该来自以下三类之一：

```text
1. i18n / product copy registry
2. BE/API/LLM 返回的真实上下文结果
3. 明确标注用途的 design-system level fallback copy
```

前端组件不应该拥有业务文案判断权。  
组件只负责展示，文案来源应该可追踪。

#### Copy Architecture

建议建立统一文案层：

```text
src/i18n/
  zh-CN.ts
  en-US.ts
  domainLabels.ts
  productCopy.ts

src/copy/
  recommendationCopy.ts
  emptyStateCopy.ts
  feedbackCopy.ts
  onboardingCopy.ts
```

同时区分：

```text
static product copy
domain enum label
LLM-generated copy
API-generated reasoning
fallback copy
test/mock copy
```

不同来源必须有不同治理方式。

#### Agent 文案原则

Agent 生成文案必须：

```text
引用真实衣物或真实上下文
避免泛泛评价
避免编造用户偏好
避免过度拟人
避免把不确定判断说成事实
```

比如不要写：

```text
这套很适合你。
```

应该写：

```text
这套避开了你不喜欢的亮色，并且使用了你最近较少穿的深灰西裤。
```

#### 工程 Guardrail

建议加入轻量检查：

```text
禁止新增已知 mock/demo 词
扫描常见硬编码 prompt
核心页面 snapshot / regression check
CI 中运行 copy lint 或脚本检查
```

可以维护一个 denylist（底线，不是完整方案）：

```text
雨天通勤 / 银蓝冷调 / demo / mock
sample outfit / local showcase / placeholder outfit
```

真正的治理方式是：用户可见文案必须进入 copy registry / i18n / API contract。

#### 成功标准

```text
生产 UI 不出现 demo/mock 文案
同一概念跨页面命名一致
默认语言不混杂
推荐理由来自真实上下文
空状态文案可解释下一步动作
新增文案能被 review 和测试发现
```

---

### Principle 7: 不审判身体，不制造身材焦虑

Aidrobe 不应该默认把女性穿搭问题解释成"修正身体"的问题。

应避免默认使用：

```text
显瘦
遮肉
遮胯
显腿长
修饰缺陷
提升比例
```

除非用户主动提出相关诉求，否则推荐不应围绕身材规训展开。

默认推荐应该围绕：

```text
舒服
得体
像自己
适合今天
能走能坐能工作
真实可穿
```

产品不应该让用户觉得：

```text
我需要被修正。
```

而应该让用户觉得：

```text
我的衣服可以更好地支持今天的我。
```

这条原则同样适用于 LLM prompt、推荐理由、insight、landing copy 和空状态。

禁止把"悦己"偷换成"变美焦虑"。  
Aidrobe 的高级感来自尊重用户主体性，而不是规训用户身体。

---

### Principle 8: 数据信任，和推荐信任一样重要（v0.8 新增）

这份文档把"可信"讲得很重，但之前的可信几乎只针对推荐本身（no fake outfit）。  
对目标用户来说，信任还有另一半，在数据层。

Aidrobe 要求用户上传整柜衣物照片，还要从她的行为里推断生活阶段、场景，  
甚至和身材相关的信息。对 20–60 女性这个群体，**隐私本身就是信任的一部分**。  
一个让她觉得"我的照片和习惯被妥善对待"的产品，才配谈"懂我"。

默认立场应该是：

```text
数据为她服务，不为别处服务。
能在端上做的，尽量不上云。
能不存的，不存。
推断结果她可见、可纠正、可删除。
```

具体要求：

```text
导入的衣物图、穿着行为、风格信号，用途只用于给她推荐
不默认用于训练、不默认对外共享、不默认用于广告画像
life-stage / 偏好 / 身材相关推断结果，用户可查看、可修正、可清空
删除账号即删除数据，并说清楚"什么时候真正删除"
Profile 里有一处人话写的数据说明，而不是法务条款堆砌
```

这条同样约束第三方视觉 / LLM 调用：

```text
发给 Qwen-VL / LLM 的内容范围最小化
第三方处理边界对用户可解释（哪些数据、为什么、去了哪）
```

一句话总结：

```text
推荐不造假，是信任的一半。
数据不滥用、可知可控，是信任的另一半。
两半都做到，"懂我"才不变成"监视我"。
```

## 6. MVP Workflow 设计

---

## Workflow 0: Cold Start / First Outfit

这一节排在 Workflow 1 之前，因为它先于"导入→Today"主闭环。  
它解决的是最容易被忽略、却决定激活成败的一段：

```text
用户刚把第一批衣服放进来，
到他第一次看到一套属于自己的可信搭配，
中间这条漏斗。
```

主路径里"第二天打开才看到 Today"有一个隐藏风险：  
用户意图最高的时刻恰恰是刚导入完那一刻，  
把魔法时刻推迟 24 小时，等于把激活机会让给流失。

### 用户目标

```text
刚把衣服放进来，就想马上看到一套属于我的搭配。
```

### 用户理想动作数

```text
0 步（导入完成即出现）
```

### 核心原则：门槛是可行性，不是数量

错误门槛：

```text
还差几件（数量）
```

正确门槛：

```text
能不能组出至少一套可信搭配（可行性）
```

数量只是可行性的代理指标。

### 可行性 Gate

一套有效搭配的最小构成：

```text
上装 + 下装 + 鞋
或
连衣裙 + 鞋
```

但"存在三件"不等于"能成一套"，必须再过四道筛：

```text
metadata 高置信（否则会推错）
彼此色调 / 正式度兼容
合今天天气
cutout 能正常渲染（渲染不出 = 违反 no-blank-image 原则）
```

Gate 判断的是过滤后的"可行搭配数"，不是 item 数。  
"图能不能渲染"是 Gate 的一部分，直接接上 Trust Acceptance。

### 三种状态

| 状态 | 触发 | 处理 |
|---|---|---|
| 0 套 | 凑不出任何可行搭配 | 按 slot 具体引导补件 |
| 1 套 | 仅 1+1+1，无可换余地 | 出这套，弱化"换一套"，提示再加几件 |
| ≥2 套 | 有多套可行 | 进入完整 Today |

State 0 的引导文案不要写"还差几件"，要按 slot 具体：

```text
你已经有 3 件上衣和 1 双鞋，
再加一条下装就能出第一套搭配。
```

把死胡同空状态变成明确的下一步动作。  
这句文案可能是整个 MVP 转化率最敏感的一句。

State 1 不要照常给"换一套"。  
1+1+1 没有可换余地，用户一点就 fail，信任当场崩。

### 冷启动推荐策略：safe over clever

冷启动与稳态的 ranking policy 是相反的：

```text
稳态：追求 diversity、避重复、给新鲜感
冷启动：挑最显然不会错的那套
```

因为代价不对称：

```text
无聊但对的首推 → 建立信任
聪明但翻车的首推 → 直接杀死用户
```

按 wardrobe 规模 / 置信度，显式切换两套 ranking policy。

### Agent 责任

```text
计算可行搭配数（含渲染可行性）
按 slot 诊断缺口
冷启动使用 safe ranking
天气过滤后做诚实兜底
确认问题按"对首推影响"排序
当场生成首套
首套理由引用真实衣物，证明它是真的
```

### 最小可用衣橱

按组合数估算（兼容性过滤后约存活 30–50%）：

| 衣橱 | 过滤前组合 | 实际可行 | 体验 |
|---|---:|---:|---|
| 1+1+1 | 1 | 0–1 | 脆弱，换一套即 fail（State 1） |
| 2+2+1 | 4 | ~2 | 勉强能换 |
| 2+2+2 + 1 外套 ≈ 7 件 | 8+ | ~4 | 换一套稳定可用（State ≥2） |
| 3+3+2 ≈ 8 件 | 18 | 充足 | 完全没问题 |

Onboarding 软目标锚在 ~7 件（2 上 2 下 2 鞋 + 1 外套），框成：

```text
传到这些，Aidrobe 就能开始每天推荐。
```

是软目标，不是硬门槛。

### 天气兜底（诚实优先）

新用户常常只传了当前没法穿的那批衣服，  
天气一过滤可能归零。

```text
若天气过滤后 = 0，但存在 season-agnostic 搭配：
出当前最合适的一套，并诚实说明：
"今天偏冷，你衣橱里合适的不多，这是目前最接近的。"
绝不硬塞，绝不伪装成完美推荐。
```

### 确认问题排序

不要把所有低置信字段都问一遍（这就是流失点）。

```text
优先问：会让首推尴尬 / 出错的（外套被认成衬衫）
跳过：不影响首套的（灰还是蓝）
预算 ≤ 2–3 个，理想 0–1 个
```

### 激活 loop 与习惯 loop 必须拆开

```text
首套搭配 = 激活时刻（同 session，导入完成当场出）
次日 Today = 习惯 loop
```

两者都需要，但不是同一件事。

并且三件事是一个包，不能拆开单独上：

```text
当场出首套
+ safe over clever
+ 可行性 Gate
```

只上"当场出首套"而不配 safe 策略，  
等于把唯一的 aha 机会押在一套可能翻车的推荐上。

### 工程现实：首套是一笔延迟与成本承诺（v0.8 新增）

"导入完成即出首套"意味着同一个 session 里要串起：

```text
Qwen-VL 理解 + metadata 补全
cutout / 渲染
LLM reasoning 生成首套理由
```

这是实打实的延迟和单次成本承诺，不是免费的产品决定。  
MVP 阶段不必精算 unit economics，但要心里有数：

```text
首套的"当场"有一个可接受延迟上限（用户在等，超过就像卡死）
需要 loading / 渐进展示，而不是白屏等全部算完
成本随导入件数线性增长，批量导入时尤其要注意
可以考虑：先出 metadata/缩略，再补 reasoning，分阶段点亮
```

把它显式记一笔，免得后面发现"当场出首套"在真机上要等很久、烧很多。

### 用户动作预算

| 动作 | 目标步数 | 说明 |
|---|---:|---|
| 导入完成看到首套 | 0 | 当场自动出现 |
| State 0 补件 | 1 | 按 slot 引导，补一件即重测 |
| 确认低置信字段 | 0–2 | 只问影响首推的 |

### 成功标准

```text
新用户导入完成后，当场看到一套真实可信的搭配
数据不足时，看到的是明确补件引导，而不是 fake outfit
首套不翻车（safe over clever 生效）
次日 Today 自然延续，不重复要求用户配置
```

## Workflow 1: First-time Import

### 重新定义导入：不是全量录入

不要让她把 50–80 件全拍一遍——那等于永远传不完，等于卸载。  
她真正在乎的只有"会真考虑穿"的那 20–30 件。

所以导入的目标是：

```text
先抓她真在穿的那批，
顺手捞出她忘了自己有的那些。
```

这比全量采集小一个量级，而且直接喂出留存钩子：  
只有先把忘了的衣服捞进来，Insights 之后才能把它们重新穿回身上。

### 真瓶颈是采集，不是识别

识别准不准从来不是衣橱 App 死掉的地方，  
愿不愿意拍完那一堆衣服才是。  
所以采集动作也应该被 agent 吞掉，而不只是识别：

```text
平铺连拍，一张图切多件
从相册里已有的穿搭照反向提取
从购物订单 / 邮件小票导入
截图导入（小红书 / IG 灵感图直接落进衣橱）
```

目标是尽快到"够用"（约 7 件就能跑，见 Workflow 0），  
而不是"传完整个衣柜"。

### 用户目标

```text
把衣服放进 Aidrobe。
```

### 用户理想动作数

```text
1–2 步
```

### 推荐流程

```text
打开 App
→ 上传 / 拍照
→ Agent 自动识别
→ 用户只确认明显错误
→ 完成
```

### 用户不应该做的事

```text
手动填写类别 / 颜色 / 季节 / 场合 / 正式度 / 风格标签
```

### Agent 责任

```text
识别衣物类别
识别颜色
识别材质
识别季节
识别场景
识别正式度
生成 display name
生成 localized name
生成 style tags
生成 cutout / thumbnail
判断低置信度字段
```

### UI 设计原则

只展示最必要确认：

```text
这几件要加入衣橱吗？
```

每件衣物卡片只提供：

```text
保留 / 删除 / 改一下
```

低置信度字段才提示：

```text
这件是外套吗？
这个颜色更像灰色还是蓝色？
```

### 成功标准

```text
用户能在 1 分钟内导入第一批衣物
用户不需要理解 metadata
用户不觉得自己在录数据库
```

## Workflow 2: Style Learning

PR #76 合并后，视觉风格学习会变成重要能力。

### 用户目标

```text
让 Aidrobe 知道我喜欢什么风格。
```

### 用户理想动作数

```text
0–1 步
```

### 推荐方式

应该允许用户自然输入：

```text
上传一张喜欢的穿搭图
收藏一张灵感图
告诉 Aidrobe：我喜欢这种感觉
```

然后 agent 自动理解：

```text
色调 / 廓形 / 风格标签 / 正式度 / 季节感 / 搭配结构 / 偏好单品
```

### Agent 责任

```text
用 Qwen-VL 理解 inspiration image
抽取 style tags
更新 style profile
影响 Today recommendation
影响 Ask Aidrobe
影响 Should-I-Buy
```

```text
已记住：你偏好干净、冷调、通勤感的搭配。
```

更进一步：

```text
这次推荐参考了你最近保存的冷调通勤风格。
```

```text
用户给一张图，后续推荐明显更接近这个风格
```

## Workflow 3: Today Recommendation

### 用户目标

```text
今天穿什么？
```

### 用户理想动作数

```text
0–1 步
```

### 推荐流程

```text
打开 App
→ 直接看到今日推荐
→ 可选择：穿了 / 换一套 / 不喜欢 / 为什么
```

### 一套，不是三套

她用 Aidrobe 就是因为不想再选了。  
给她三套去挑，等于把决策疲劳换个壳塞回去给她。

所以 Today 默认只给一套她能信的，  
配一个秒级"换一套"应付偶尔不对味的日子。

```text
这是 decision automation，
不是给她一份菜单让她继续选。
```

### 主屏只应该有四个核心动作

```text
穿这套 / 换一套 / 不喜欢 / 为什么推荐
```

不要在主屏放太多入口。

### Agent 责任

```text
读取天气 / 位置 / 最近穿着 / 用户偏好
读取 visual style profile
读取 wardrobe graph
按 wardrobe 规模 / 置信度切换 ranking policy
  · 冷启动：safe over clever（挑最显然不会错的一套）
  · 稳态：diversity constraints（避重复、给新鲜感）
避开 disliked items
生成 outfit / 生成理由 / 生成 fallback
```

### 推荐理由格式

理由要具体、来自真实上下文，不要泛泛文案。  
正反例规范统一见 §6.5 Tone of Voice。一句话原则：

```text
回答"为什么是这套 / 为什么适合今天 / 为什么像我"，
而不是"很好看 / 很百搭 / 很适合你"。
```

### 不足数据状态

如果衣服不够，不要展示 fake outfit，按 slot 给出明确补件引导（见 Workflow 0 三状态）。

### 成功标准

```text
用户打开 App 后 3 秒内理解今天建议
用户不需要输入问题
用户相信这套是真的基于自己衣橱推荐
```

## Workflow 4: Recommendation Feedback

### 用户目标

```text
告诉 Aidrobe 这套行不行。
```

### 用户理想动作数

```text
1 步
```

### 反馈设计

主操作：

```text
穿了 / 换一套 / 不喜欢
```

点"不喜欢"后再展开原因：

```text
太正式 / 太休闲 / 太热 / 太冷 / 颜色不喜欢 / 不像我 / 刚穿过
```

不要一开始就让用户填反馈表。

### Agent 责任

```text
记录事件
识别负反馈原因
更新短期推荐状态
更新长期偏好记忆
更新 ranking signal
更新 wardrobe graph
避免下次重复
```

### 成功标准

```text
用户点一次"不喜欢"，下一套明显修正
用户不需要重新描述需求
```

### 不要把命压在"穿了"按钮上

目标用户不会每天回来打卡今天穿了什么。  
这是事实，不是靠提醒就能解决的依从性问题。

而"越来越懂我"这个核心承诺，数据源恰恰是"她实际穿了什么"。  
如果只靠她主动点"穿了"，这个信号会长期稀疏，后台一堆 learning 就被饿着。

所以：

```text
把早上点的"穿这套"当成意图信号，不是确认信号
被动推断：看了某套 + 没换 + 没提特殊需求 → 大概率穿了
晚上最多一次轻量补问（"昨天那套穿了吗？"），不强制
即使没有 wear 数据，推荐也要能 graceful degrade
```

learning 能力不能悬在一个没人按的按钮上。

### Passive Learning Strategy

穿了按钮是显式信号，但不是 learning 的唯一来源。

目标用户不会每天主动打卡，所以系统必须采用：

```text
被动信号优先，主动输入兜底。
```

可以使用的被动信号：

```text
打开 Today 的时间
是否查看主推荐
查看后是否换一套
是否点不喜欢
是否进入 outfit detail
是否保存 / 分享
是否围绕同一套继续 Ask
是否多次提出类似 override
当天时间 / 天气 / 工作日 / 周末
```

穿着推断可以采用弱规则：

```text
看了某套 + 没换 + 没点不喜欢 + 没提出特殊需求
→ 大概率接受 / 可能穿了
```

但不能把弱推断当成强事实。  
它应该进入低权重 learning，而不是直接写成强偏好。

主动确认只在轻量场景出现：

```text
昨天那套穿了吗？
穿了 / 没穿 / 换了别的
```

这类补问最多偶尔出现，不能成为使用负担。

核心原则：

```text
能推断就不问。
推断不确定，再轻问一句。
即使没有 wear 数据，推荐也要 graceful degrade。
```

### 用户目标

```text
我有一个特殊穿搭问题。
```

### MVP 定位

Ask 不是主路径，而是辅助入口。

Today 负责默认推荐。  
Ask 负责特殊需求。例如：

```text
今晚约会穿什么？
这件外套怎么搭？
明天面试能穿这套吗？
我想穿得不那么正式
```

### 用户理想动作数

```text
一句话
```

### Agent 责任

```text
理解用户问题
读取 wardrobe context
读取 preference memory
读取 conversation state
围绕 focused item 回答
支持多轮 refinement
记住明确长期偏好
```

### UI 原则

Ask 不应该像普通 chatbot。它应该像：

```text
一个懂你衣橱的 stylist
```

回答里应该尽量引用真实衣物：

```text
你可以用那件深灰西裤搭白衬衫，再加黑色乐福鞋。
```


```text

```

### MVP 定位

Trips 不应该进入 MVP 主路径。它是后续高价值场景。

但设计理念现在就要定好：  
旅行不是表单，而是一条轨迹。

### 用户目标

```text
我要去一个地方，帮我少带但穿对。
```

### 用户理想动作数

```text
一句话
```

例如：

```text
下周去东京 5 天，两天商务，周末逛街，帮我打包。
```

### Agent 责任

```text
提取目的地 / 日期
识别场景
查天气
理解行程节奏
选择真实衣物
规划每日 outfit
减少重复 / 减少行李
提示缺失单品
```

### 圆周轨迹启发

旅行体验不应该像填报表。更好的组织方式是一条围绕行程展开的轨迹：

```text

Weather-aware adjustments
```

```text

```

等 Today 主闭环稳定后，再独立成 Trips workflow。

## Workflow 8: Wardrobe Health / Insights

### 重新定位：Insights 是留存钩子，不是次要功能

对目标用户来说，"把忘了的衣服重新穿起来"不是边角功能，  
而是她每天回来的真正理由之一。

```text
"这件你买了三个月没穿过，今天天气正合适。"
```

这一句同时给了她两样东西：

```text
被看见——系统记得她忘了的衣服
没浪费的小满足——那点"总穿那几件"的愧疚被温柔化解
```

它和导入是一个闭环：  
导入时捞出忘了的衣服，Insights 把它们重新穿回身上。

但它仍然不是 dashboard。  
它是 Today 里自然长出来的一句话，不是一个要她去"看报表"的页面。

### 用户目标

```text
我想知道我的衣橱哪里有问题。
```

### MVP 定位

Insights 不应该成为复杂 dashboard。  
它应该是被动出现的轻量建议。例如 Today 下方：

```text
你最近一直在穿同一条黑裤子。
这周可以试试那条灰色西裤。
```

或者 Should-I-Buy 中：

```text
你已经有 4 件类似黑色上衣，这件可能重复。
```

### Agent 责任

```text
发现重复 / 缺口 / 未穿衣物 / 季节不足 / 过度依赖某些单品
转成轻量建议
```

### UI 原则

不要羞辱用户。语气规范见 §6.5（避免"你浪费了很多衣服 / 你的衣橱不健康"）。

### 成功标准

```text
Insights 帮助用户行动，而不是制造焦虑
```

## 6.5 Tone of Voice / Copy Philosophy

Aidrobe 的文案系统要服务"悦己"和"可信"，而不是服务"炫技"。  
这一节是全文档**唯一**的文案正反例出处，其他 workflow 一律引用这里，避免重复。

### 推荐文案

推荐文案要回答：

```text
为什么是这套？为什么适合今天？为什么像我？
```

不要只输出情绪价值：

```text
这套很好看 / 这套很百搭 / 这套很适合你
```

要输出基于真实上下文的短理由：

```text
今天有雨，所以避开了浅色鞋。
这件外套你最近没穿过，但和黑裤子兼容度高。
这套更接近你保存过的冷调通勤风格。
```

### 空状态文案

空状态不是失败页，而是下一步引导。

不要写：

```text
暂无数据 / 请添加更多衣物
```

要写：

```text
你已经有 3 件上衣和 1 双鞋。
再加一条下装，就能生成第一套搭配。
```

### 反馈文案

降低心理负担。

不要写：

```text
请评价本次推荐准确度 / 请填写不满意原因
```

要写：

```text
这套哪里不合适？
太正式 / 太热 / 颜色不喜欢 / 不像我
```

### Insight 文案

帮助行动，不制造焦虑。

不要写：

```text
你的衣橱不健康。你浪费了很多衣服。
```

要写：

```text
这些单品最近没怎么出现，可以重新利用。
你已经有足够多黑色上衣，下一次可以优先考虑外套。
```

### Landing / Brand Copy 候选

可进入品牌/落地页候选，但不应散落硬编码在功能组件里：

```text
今天，穿成喜欢的自己。
穿给自己看，取悦每一天。
打开衣柜，也打开今天的自己。
每天，都做自己的灵感缪斯。
衣橱不只是收纳，是我爱自己的方式。
衣以载心，容以悦己。
```

它们应该进入 copy registry / i18n，由产品统一治理。

## 10. MVP Feature Scope（按发布顺序，不按愿望清单）

这一节不再用 Must / Should / Could 这种容易越堆越满的分法，  
改成诚实的**发布顺序**。判断依据见 §4.5：离核心闭环越近，越靠前。

### P0：核心闭环，缺一不可

这一组就是 §4.5 那条不可再缩减的核心，加上守住它的信任底线。

```text
衣物导入（先抓在穿的 + 捞忘了的）
AI metadata + cutout 渲染
可行性 Gate + 三状态（0 / 1 / ≥2）
导入即出首套（safe over clever）
次日 Today 单套推荐 + 真实理由
穿了 / 换一套 / 不喜欢
信任底线：no fake outfit / no blank image / no hardcoded copy / 不编造衣物
```

少了 P0 里任何一项，"导入 → 可信首套 → 次日还想打开"这条线就断了。

### P1：让"越来越懂我"真正成立

核心闭环跑起来之后，紧接着要补的是 learning 和黏性。

```text
被动 learning（不依赖"穿了"按钮，见 Workflow 4）
结构化负反馈原因
visual style learning 接入 Today（PR #76）
resurface insight（把忘了的衣服重新穿回身上，留存钩子）
一句话 context override
recommendation diversity（稳态 ranking）
safe image fallback
数据可查 / 可删 / 数据说明（Principle 8 的最小落地）
```

P1 决定的是产品能不能从"能用一次"变成"值得每天回来"。

### P2 / Later：高价值但不抢核心

```text
Should-I-Buy（情境入口，非一级 tab）
Trips / Packing（先在 Ask 里支持一句话）
advanced wardrobe health
cost-per-wear
outfit calendar
share card
advanced shopping evaluator
```

### 明确不进 MVP

```text
复杂 dashboard
复杂风格问卷
复杂用户手动配置
完整旅行行程系统
完整社交分享系统
```

### 特别说明：life-stage-aware recommendation 不是 v1 capability

它在 v0.7 里被放进了 Should Have，这是 over-promise。  
冷启动时系统几乎没有行为信号去判断用户更接近哪个生活阶段（见 §0.5.1），  
所以 early 阶段它大概率不会稳定触发。

诚实定位：

```text
v1：所有 20–60 女性共用同一套不审判、不催买、给一套可信首推的体验
后续：积累足够行为后，再让推荐逐渐贴近她的生活阶段
```

不要把 life-stage-aware 写进 MVP 验收。它是 north-star，用来指导取舍，不是交付项。

## 11. PR #76 的产品定位

PR #76 不应该只是一个技术能力，它应该被定义为：

```text
无感风格学习能力
```

也就是：

```text
用户给 Aidrobe 一个视觉偏好信号，Aidrobe 后台理解并影响推荐。
```

它最适合放在三个位置：

### 1. Onboarding 后半段

不要做问卷，而是：

```text
给 Aidrobe 一张你喜欢的穿搭图
```

可跳过。

### 2. Ask Aidrobe 中

用户可以说：

```text
我喜欢这种风格，帮我以后参考
```

### 3. Today 后台推荐

style profile 影响推荐，但不要把技术细节暴露出来。推荐理由可以轻量提到：

```text
这套参考了你最近保存的冷调通勤风格。
```

## 12. MVP 验收标准

MVP 不应按功能数量验收，应该按主闭环验收。

### Core Acceptance

```text
一个新用户能导入衣服
系统能自动整理
导入完成即看到首套，次日 Today 持续
用户能一键反馈
下次推荐能体现反馈
```

### Trust Acceptance

```text
没有 fake outfit
没有 demo prompt
没有硬编码用户可见业务文案
没有混合语言 mock copy
没有空白图片
没有不可用按钮
没有编造衣物
没有泛泛推荐理由
```

### Privacy Acceptance（v0.8 新增）

```text
用户能查看自己被采集了什么数据
用户能删除数据 / 删除账号，且说清楚何时真正删除
life-stage / 偏好 / 身材相关推断结果可纠正、可清空
数据用途有人话说明，而不是只藏在隐私政策里
默认不用于训练 / 不对外共享 / 不做广告画像
```

### Simplicity Acceptance

```text
用户不需要配置风格
用户不需要维护标签
用户不需要理解系统逻辑
用户不需要每天输入问题
```

### Intelligence Acceptance

```text
推荐使用真实衣物
推荐考虑天气
推荐考虑最近穿过
推荐考虑偏好
推荐能解释
推荐能从反馈学习
```

## 16. 最终结论

Aidrobe 现在最重要的问题已经不是：

```text
还能加什么功能？
```

而是：

```text
如何让用户几乎不操作，但系统越来越懂他？
```

更进一步，这一版（v0.8）想锁住的判断是：

```text
MVP 不是这份文档里所有想法的总和，
而是"导入即出首套"那一条闭环。其余都是排序。
```

MVP 应该追求：

```text
少入口 / 少配置 / 少解释负担 / 少手动维护 / 少硬编码文案
```

同时后台拥有：

```text
强识别 / 强记忆 / 强规划 / 强反馈学习 / 强推荐解释
```

并且守住两条信任：

```text
推荐不造假。
数据不滥用、可知可控。
```

产品最终应该让用户感受到：

```text
我只是正常生活，Aidrobe 自动理解我。
今天，我更容易穿成喜欢的自己。
```

这才是 Aidrobe 最小但最优的 MVP。
